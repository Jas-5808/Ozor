# План: QR-код заказа и API по коду

## Цель
- При сканировании QR выходит **цифра** вида `1737123456789123`.
- **POST** запрос на API с телом `{"qr_code": "1737123456789123"}`.
- Ответ API в формате:
```json
{
  "success": true,
  "msg": "Buyurtma topildi",
  "data": {
    "id": 12345,
    "full_name": "Alisher Navoiy",
    "phone": "998901234567",
    "additional_phone": "998909876543",
    "region": 11,
    "district": 1101,
    "address": "Chilonzor 10-kvartal, 5-uy",
    "comment": "Qo'ng'iroq qiling",
    "delivery_price": 35000,
    "total_price": 250000,
    "total_count": 2,
    "created_at": "2025-01-20 14:30:00",
    "items": "Mahsulot nomi x 2 = 250 000 so'm"
  }
}
```

|-----------|-----|--------|

| Поиск заказа по id | `repository.get_order_by_id(order_id)` | Есть поиск по UUID. Поиска по строке «qr_code» **нет**. |

## 2. Чего нет (нужно сделать)

### 2.1 Цифра в QR и привязка к заказу

- Сейчас в QR не 16-значная цифра, а URL или `order_number`.
- Нужно:
  - **Либо** ввести поле в БД (например `qr_code` на заказе) — уникальная строка вида `1737123456789123`, генерируется при создании заказа (или миграция для старых).
  - **Либо** договориться о формате кода без нового поля (например кодировать `order.id` или `order_number` в 16 цифр) и везде использовать один и тот же алгоритм генерации/поиска.

Без этого нельзя: по отсканированной цифре однозначно найти заказ и вернуть нужный JSON.

### 2.2 API: POST по qr_code

- Эндпоинта вида `POST /...` с телом `{"qr_code": "1737123456789123"}` **нет**.
- Нужно:
  - Добавить маршрут (например в `warehouse` или отдельный публичный/складской): `POST /warehouse/order-by-qr` или `POST /shop/order/by-qr`.
  - Принять `qr_code`, по нему найти заказ (по полю `qr_code` или по декоду из цифры).
  - Вернуть ответ в формате `{ success, msg, data }` как выше.

### 2.3 Формат ответа `data`

- `id`: у вас сейчас UUID; в примере — число (12345). Решение: отдавать `id` как число (например хэш/суффикс UUID) или как строку UUID — нужно зафиксировать.
- `full_name`, `phone`, `comment`, `delivery_price`, `total_price`, `total_count`, `created_at`, `items` — **есть** данные в Order/items, нужно только собрать в один объект и отформатировать (дата, строка items).
- `additional_phone`: в Order **нет** поля. Варианты: не отдавать (null/пусто), либо добавить поле в Order и в форму заказа.
- `region`, `district`: в Order есть только строки `city`, `order_region`. Числовых кодов (11, 1101) **нет**. Варианты: отдавать строки в других полях; или ввести справочник регионов/районов с id и хранить в заказе `region_id`/`district_id`.

### 2.4 Этикетка (PDF)

- После появления «цифры» заказа нужно в этикетке в QR подставлять **именно эту цифру** (а не URL и не order_number), чтобы скан давал `1737123456789123`. То есть в `get_order_label_pdf()` передавать в `build_label_pdf(..., qr_content=эта_цифра)`.

### 2.5 Фронт / сканнер

- Если сканнер только выводит строку — то клиент (приложение или страница) должен сам слать POST с `{"qr_code": "1737123456789123"}` на ваш API и показывать ответ. Отдельная страница «просмотр заказа по QR» на фронте — по желанию (например форма с полем ввода кода + кнопка «Найти» или автоматический запрос при переходе по URL с кодом в пути).

## 4. Краткая сводка

- **Есть:** генерация QR в PDF, модель Order с основными полями, логика этикетки, возможность собрать почти все поля для `data`.
- **Нет:** цифра вида `1737123456789123` в QR и способ её сопоставить с заказом; POST API по `qr_code`; формат ответа с `region`/`district`/`additional_phone` (и при необходимости доработка модели).

Дальше можно зафиксировать: 1) как именно получаем цифру (поле в БД или кодирование), 2) нужны ли в ответе `additional_phone` и числовые `region`/`district`, и затем реализовать пункты 1–5 (и при необходимости 6–7).
